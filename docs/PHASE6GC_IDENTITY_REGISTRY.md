# Operator identity registry — Phase 6G-C

Included in the PR #1 development checkpoint. This is an immutable mapping of
opaque tenant/customer references, not external authentication, financial balance
creation, retroactive ownership attribution or issued-wallet acceptance. It is
connected to operator-only [Solana root/claim reservations](PHASE6GC_SOLANA_REGISTRY.md).
External authorization, issued wallets and financial/signing consumers remain incomplete.

## Identity and authority

`CustodyTenant` has a generated UUID and an exact globally unique reference.
`CustodyPrincipal` has a generated UUID, immutable tenant membership, exact
tenant-scoped customer reference and unique ledger owner ID `p1:<principal UUID>`.
The ID is generated by the service and enforced independently by PostgreSQL;
registration does not accept a caller-selected existing ledger owner.

References preserve exact UTF-8 code points and case. No Unicode normalization,
case folding or whitespace trimming changes an identity. Empty, over-64-character,
NUL-containing and leading/trailing ASCII-whitespace references are rejected.
PostgreSQL installs C collation on the two new reference columns in migration0033;
the catalog is tested. Its portable migration state remains backend-neutral so
the existing SQLite demo can still migrate. Protected registry writes/resolution
require PostgreSQL; SQLite is not a registry security or custody acceptance target.

Management command examples (privileged operator environment only):

```sh
python manage.py custody_identity tenant --tenant-reference opaque-org --operator-ref ops-ticket-123
python manage.py custody_identity principal --tenant-id <uuid> --customer-ref opaque-id --operator-ref ops-ticket-123
python manage.py custody_identity resolve --tenant-id <uuid> --principal-id <uuid>
```

Operator filesystem/database credentials remain the authority for these commands.
`--operator-ref` is supplied audit attribution, not proof of an authenticated human.
No Django/public tenant API, service token, login, RBAC or signer permission is
added. `resolve_principal` checks both tenant and principal UUID; its caller must
obtain the tenant from a trusted authorization context before future external use.
Django admin is view-only even for superusers. Database owners and privileged
application code remain trusted; this is not a guard against disabling triggers.

## Registration, collision and audit boundary

Supported registration runs in its own READ COMMITTED transaction. Services reject
caller `atomic()` blocks and disabled autocommit; SQL also rejects older-snapshot
isolation levels. Principal INSERT locks all five legacy ownership tables with
SHARE ROW EXCLUSIVE NOWAIT before checking any of them:

- LedgerAccount USER owner IDs;
- UserWallet and WithdrawalRequest user IDs;
- MpcCustodyAccount and MpcDerivationReservation customer references, including
  prior reservations that never became an account.

An active legacy writer or conflicting maintenance lock causes retryable failure;
no owner row/audit is committed. A previously committed matching identity causes
rejection, never adoption/backfill. A registration that acquires the locks first
blocks concurrent legacy writers until its transaction ends. Real separate
connections and `pg_blocking_pids` verify both orders. This guarantees the
serialized registration point; later privileged legacy writes remain trusted.
It is not permanent authorization of every subsequent use of a `p1:` string.

Ops AddressBalance is a derived snapshot and is deliberately not ownership
authority or part of these scans. No legacy account, wallet, reservation, journal,
posting or balance is relabelled. The service creates no financial account or
wallet. New identities must be explicitly integrated with the authoritative ledger,
custody evidence and authenticated caller scope before any issuance or posting.

Creation and its AdminActionLog record commit together. Audit failure rolls back
creation; duplicate retries return the original row without another birth event.
The existing best-effort audit helper and its optional external hooks are not
called. Direct privileged SQL writes are outside this service audit guarantee.

Models, admin and PostgreSQL reject identity mutation/deletion, including tenant,
UUID, customer reference, ledger ID and creation time. A populated registry blocks
migration downgrade: off-database signer evidence could already reference these
IDs even if no local financial rows exist. Migration0033 atomically creates both
tables, explicit PostgreSQL collations and guards; it performs no backfill or
existing-table rewrite. Empty downgrade/forward and preserved historical rows are
tested. Backup restore/coherent database rollback is not prevented by this registry.

## Evidence and limits

47 PostgreSQL tests passed in18.48s; a separate reviewer independently reran all47
in15.44s with no P0/P1 found within this operator-only boundary. They cover exact
tenant scoping, duplicate/concurrent births, canonical generated IDs, raw SQL/FK/
nil/trim/immutability negatives, both legacy-writer orders, audit rollback, isolation,
admin HTTP mutation/bulk rejection and migration/history preservation. Fresh SQLite
demo migration succeeded and protected registration was refused as expected.
The full backend suite passed **710 tests in149.78s**. The migration regression
was then strengthened with a nonzero balanced journal, original account/posting
snapshots and unchanged7.25-unit balance; that case passed separately in2.14s.

Registry scans, especially legacy MPC customer-reference lookups, do not establish
population scalability. Registration may briefly block legacy writes while holding
the five relation locks, and contention/maintenance can reject it. Authenticated
external principals, treasury/legal ownership policies, Solana root/claim database
integration, customer issuance, actual financial attribution, generation witness,
Hot/Warm/Cold controls and the whole-phase acceptance remain unfinished.

The earlier source checkpoint `e5b82faa` passed Fast40579867138 and full40579857716:
all14 jobs, 227 cryptographic scenario calls, zero skips, original-store upgrade
425.729s. Those gates predate this registry; new source needs its own checks.
No production/mainnet/customer-fund activation or phase merge is authorized.
